# create-exodra

Scaffold a new Exodra application. The CLI asks at a prompt (Next.js style): run it and
answer a few questions, or pass flags to skip the prompts.

Everything it writes is the **schema core**: a schema and a machine built with
`createExoMachineBuilder` from `@exodra/core`. The default (Vite) scaffold declares its
schemas with `exoJsx` from `@exodra/jsx`, which `@exodra/vite-plugin` compiles away; the
`--ssr` scaffold and everything the `exodra` CLI generates build schemas with
`createExoSchema` and contain no JSX, so they compile without a JSX transform.

## Quick Start

```bash
# Using npm
npm create exodra@latest my-app

# Or directly
npx create-exodra my-app
```

If you omit a project name you'll be prompted for one. Without flags, the CLI prompts
for TypeScript, ESLint, Tailwind CSS, a `src/` directory, SSR, App Router, and the
import alias.

## CLI

```bash
npx create-exodra [project-name] [options]
```

### Options

- `--ts`, `--typescript` - use TypeScript
- `--js`, `--javascript` - use JavaScript
- `--tailwind` - set up Tailwind CSS
- `--eslint` - set up ESLint
- `--src-dir` - use a `src/` directory
- `--ssr` - scaffold a server-side-rendered app (`@exodra/ssr` + hydration)
- `--app` - use the App Router (`@exodra/router`)
- `--import-alias <alias>` - import alias to use (default `@/*`)
- `--use-npm` / `--use-yarn` / `--use-pnpm` / `--use-bun` - choose the package manager

Any option you don't pass is asked interactively. Passing a flag skips that prompt.

### Examples

```bash
# TypeScript app with the App Router and Tailwind, no prompts
npx create-exodra my-app --typescript --app --tailwind

# JavaScript app, no App Router
npx create-exodra simple-app --javascript

# Server-side-rendered app
npx create-exodra my-ssr-app --ssr
```

After scaffolding:

```bash
cd my-app
npm install
npm run dev
```

## The `exodra` CLI

The package also installs an `exodra` binary for scaffolding inside an existing project:

```bash
npx exodra component Button      # create a component (alias: c)
npx exodra page Home             # create a page (alias: p)
npx exodra api hello             # create an API route (alias: a)
npx exodra config                # create exodra.config.js
```

Common options for `component` / `page`: `-d, --dir <path>`, `-t, --typescript`,
`--naming <PascalCase|kebab-case|snake_case>`.

`component` and `page` emit **schema core** modules — the same shape the `--app`
scaffold writes — so a generated page drops straight into the generated route
table. A page is a machine **default-exported** from its module; a
component is a named machine export, filled by its parent with
`c.one(P.slot, Name)` or repeated with `c.list(P.slot, Name, count)`. Neither
contains JSX, so neither needs the Babel plugin to compile. With `-t` the files
carry type annotations; without it they are the same code with the types dropped.

**There are no props.** `createInitialState` is `(exonode, index) => state`: an instance is
handed its position and nothing else, so the data it shows is read by index from
somewhere the caller put it — which is why the component generator emits an array
beside the component — and the machine's `wire` writes the ports from that state. A page
receives the match that selected it as the params of its wire.

```tsx
// src/pages/Home.tsx, from `npx exodra page Home -t`
import { createExoMachineBuilder, createExoSchema } from '@exodra/core';
import type { TExoMachineNode, TExoTextPort } from '@exodra/core';

const PAGE_SCHEMA = createExoSchema(b => {
  let heading!: TExoTextPort;
  b.el('div', { class: 'page' }, d => {
    d.el('h1', null, h => {
      heading = h.textPort();
    });
    d.el('p', null, p => p.text('Welcome to the Home page.'));
  });
  return { heading };
});
const mPage = createExoMachineBuilder<TExoMachineNode>(PAGE_SCHEMA);
mPage.wire(c => {
  c.text(PAGE_SCHEMA.ports.heading, 'Home');
});
export default mPage.done();
```

## What gets generated

A standard (non-SSR) app uses Vite with `@exodra/vite-plugin` and depends on
`@exodra/core`, `@exodra/jsx` and `@exodra/dom` (plus `@exodra/router` when the
App Router is enabled). The generated `src/main` is a machine rendered
through a module-level `withExoCompiler(new ExoDomBackend())` — with `--app`,
`withExoChildList(withExoCompiler(new ExoDomBackend()))`, because the outlet and the nav open a
child list and a backend without that pack refuses with `EXO0109`: its schema is an `exoJsx` declaration
built when the module loads, and the machine's `wire` fills its ports. The generated
`tsconfig.json` sets `jsxImportSource: "@exodra/jsx/schema"`, which types the dialect.

With `--app`, the pages under `src/pages` are machines default-exported
from their modules and the route table is generated by the Vite plugin and imported
as `virtual:exodra-routes`. `src/router.ts` constructs the router and nothing else,
so a page can import it without importing the module that renders the app. `src/main`
provides the router with `provideExoRouter(c, router)`, places the route boundary with
`c.one(port, ExoOutlet)`, and builds the nav as `ExoLink` machines —
`links.insert(c.build(ExoLink, i, { to, label, currentWhen: 'exact' }))` — real
`<a href>` markup that the router takes over on a plain left click, while a
modifier-click or a new-tab click stays the browser's. A page receives the match that
selected it as the params of its wire.

An SSR app (`--ssr`) depends on `@exodra/ssr` and `@exodra/string` instead, with an
Express dev/prod server. **One** machine serves both halves: `renderExoPage(App, {
params })` turns it into HTML plus a state script on the server — the machine's wire
records what it started from with `c.inject(EXO_SSR_RESPONSE)?.setState(...)` — and on
the client `readExoStateScript()` reads that back and a
`withExoHydration(new ExoDomBackend())`'s `hydrate(App, root, params)` adopts the
server's nodes — taken over rather than rebuilt, so only listeners are added.
Hydration is a pack rather than a method, so a client-only app never pulls the
adopters into its bundle.

## Writing Exodra components

A component is one value with two halves: a **schema** built once at module load,
and a **machine**. `createInitialState` runs once per instance and returns the state
the instance keeps; transitions turn that state into port writes; handlers change it.

```ts
import { createExoMachineBuilder, createExoSchema } from '@exodra/core';
import type { TExoEventPort, TExoMachineNode, TExoTextPort } from '@exodra/core';
import { ExoDomBackend, withExoCompiler } from '@exodra/dom';

const backend = withExoCompiler(new ExoDomBackend());

const COUNTER_SCHEMA = createExoSchema((b) => {
  let caption!: TExoTextPort;
  let click!: TExoEventPort;
  b.el('div', { class: 'counter' }, (d) => {
    d.el('span', null, (s) => {
      caption = s.textPort();
    });
    d.el('button', { class: 'btn' }, (btn) => {
      click = btn.eventPort('click');
      btn.text('+1');
    });
  });
  return { caption, click };
});
const mCounter = createExoMachineBuilder<TExoMachineNode, unknown, { count: number }>(
  COUNTER_SCHEMA
);
mCounter.createInitialState(() => ({ count: 0 }));
const show = mCounter.transition((c) => {
  c.text(COUNTER_SCHEMA.ports.caption, `Count: ${c.state.count}`);
});
mCounter.wire((c) => show(c));
mCounter.on(COUNTER_SCHEMA.ports.click, (c) => {
  c.state.count += 1;
  show(c);
});
const Counter = mCounter.done();

backend.render(Counter, document.getElementById('app') as HTMLElement);
```

The write doors are the whole set: `c.attr(port, value)` fills an attribute port,
`c.text(port, value)` a text port, `c.unsafeHtml(port, markup)` raw markup, and
`c.on(port, handler)` attaches a listener. Following data that lives outside the
machine is an **effect** that draws through a transition and subscribes, returning
the unsubscribe: `m.effect((c) => { show(c); return store.subscribe(() => show(c)); })`.

Children are placed by the calls that take a component: `c.one(port, C)` for one
instance, `c.list(port, C, count)` for a fixed number of them — a **count**, not an
array — and, for a list that changes, a child list opened with `c.childList(port)` in
`createInitialState` and reconciled from a transition with
`reconcileExoOrder(rows, shown, items, items, (item, i) => c.build(C, i))` from
`@exodra/list-reconcile`, by the identity of the item objects. Nothing scaffolded here
uses the reconciler, so `@exodra/list-reconcile` is not among the generated
dependencies — add it when a list has to grow. A reconciled list hydrates: the served
rows are adopted as long as the effect that drives it draws when it starts.
